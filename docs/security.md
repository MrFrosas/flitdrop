# Security model

## What is guaranteed

**End-to-end encryption between the phone (web page) and the computer.**

- Algorithm: XChaCha20-Poly1305 (AEAD), from the audited @noble/ciphers library, identical on the browser and the computer.
- Key: 32 random bytes generated by the computer at pairing, carried only in the **fragment** of the QR code URL (`/s/#id.key`). A URL fragment is never sent in HTTP requests, so the key never travels over the network, even in the clear locally.
- Every message carries a **contextual AAD** (`wd1|device|purpose|transfer|chunk#`): a captured ciphertext cannot be replayed on another route, for another device, or at another file position.
- JSON envelopes carry a timestamp (2-minute window) and a unique `jti` (anti-replay cache).
- A tampered, truncated or reordered chunk is rejected (Poly1305 tag + AAD). Tested.

**Locked admin surface.** The desktop interface and admin API are reachable only from the machine itself (loopback check) and only with a token (query once, then HttpOnly SameSite=Strict cookie). Constant-time comparisons. The real-time WebSocket requires the same token and loopback.

**Defensive disk writes.** File names are sanitized (path traversal, forbidden characters, Windows reserved names, bounded length), collisions de-duplicated, written to a `.tmp` then atomically renamed with an exclusive reservation. Max file size is enforced.

**Anti-abuse.** The chunk route rejects unknown devices before reading the body. Rate limits per IP. Bounded JSON bodies. Devices are revocable in one click (key destroyed).

## Per-PC binding and QR safety (v0.2 → v0.3)

- **Each computer has a secret `instanceId`.** Every pairing is bound to it. A phone paired to computer A is cryptographically refused by computer B (HTTP 409), even on the same Wi-Fi. The phone also pins the `instanceId` and refuses a different computer answering at the same address. "Reset this PC" rotates it and wipes all pairings, clipboard history and pending files (for lending/selling the machine).
- **The QR key is single-use (rotation on first hello).** The key in the QR is only an ephemeral *pairing* key. On the phone's first `hello`, the computer generates a fresh **session key**, returns it encrypted under the pairing key, and replaces the stored key. So **a photo of the QR is worthless once the real phone has connected**: the pairing key no longer authenticates anything. Pending (un-scanned) QRs also expire in ~3 minutes, enforced by a timer. While the pairing window stays open and visible, the computer replaces the code 30 seconds before it expires (the old one stays valid until its own 3 minutes are up); no new code is made while the window is closed or hidden. A phone that scans an expired code is told so (`pairingExpired`): the computer remembers the ids of expired codes in memory for one hour, never on disk.
- **Restrictive file permissions.** `~/.flitdrop` is created `0700` and its sensitive files (`config.json` with the tokens, `devices.json` with the keys, clipboard history and images) are written `0600`: no effect on Windows ACLs, real protection on macOS/Linux against other users and sync tools.

## Windows firewall check and repair

- **Check (read only).** When the pairing QR has been visible for 45 seconds and no phone has opened the page, the Windows app runs ONE hidden PowerShell (`-NoProfile -NonInteractive -EncodedCommand`, 8 s timeout, full path under `%SystemRoot%`): `Get-NetConnectionProfile` for the network type of the interface that carries the QR address, and the firewall COM object (`HNetCfg.FwPolicy2`) for the profile settings and the rules whose program is `Flitdrop.exe` (the exact path is compared in Node, case-insensitive, `%VAR%` expanded). Nothing is changed. At most once per opening of the pairing window and once every 10 minutes. Code: `packages/core/src/firewall.ts`.
- **Repair (only on a click).** « Fix it » starts one elevation request (`Start-Process powershell -Verb RunAs`, the UAC prompt names Windows PowerShell). The elevated script removes only the inbound **Block** rules whose program is this exact executable, removes a previous rule with our name, and adds one inbound **Allow** rule « Flitdrop (réseau local) » (group `Flitdrop`): this program, TCP, Private and Public profiles, remote address `LocalSubnet`. The network category is never changed, no other program is touched, no port is opened for anything else. The executable path is passed inside the Base64 (UTF-16LE) encoded command, quoted as a PowerShell literal (all four apostrophe forms doubled), so spaces, accents and apostrophes in the user folder cannot break out. The admin API endpoint refuses a repair unless the last check found a problem.
- **Uninstalling** leaves the allow rule (removing it would need a second elevation). It only matches that executable path and only the local subnet: a program later placed at the same path in the user folder would get the same LAN access. Accepted: writing there already requires running as the user.
- **macOS**: the application firewall is off by default and no blocking case was found; nothing is done. **Linux**: nothing is done (no firewall is active by default on common desktops, and there is no common way to configure one).

## Accepted trade-offs

1. **The iOS Shortcut routes (`/api/shortcut/*`) use a bearer token, without application-layer encryption**, because the Shortcuts app cannot do crypto. On a hostile Wi-Fi, content sent by the Shortcut is readable by a local network observer. This channel is now a **toggle in Settings** (default on), so you can turn it off on untrusted networks; the rest of the app is end-to-end encrypted regardless.
2. **No TLS on the LAN**, on purpose: a self-signed certificate triggers blocking warnings on mobile. The application-layer AEAD covers confidentiality and integrity of the data; HTTP metadata (paths, sizes, timing) stays visible on the LAN.
3. **Shared localhost / same-user malware.** A program running under your own OS user can read `~/.flitdrop` and drive the loopback admin API. This is the universal desktop-app threat model: once code runs as you, local-data confidentiality is lost by definition; no app can fully prevent it. The `0600` perms above shrink the blast radius (other users, backup/sync tools); a future macOS App Sandbox / hardened-runtime build would further contain the app itself from being weaponized.

## Automated security tests

`npm test` covers: tampered chunk → 403, replayed envelope → 403, unknown device → 403, cross-context AAD → failure, stale timestamp → failure, invalid Shortcut token → 401, admin without token → 401, path traversal → neutralized, oversized file → 413, hard cap on the anti-replay cache, atomic file-name reservation.

## Adversarial attack review (July 2026)

A four-angle adversarial review (auth/crypto, filesystem, denial of service, web-client security), each finding independently counter-verified against the real code, found 3 false positives and **4 real defects, all fixed the same day**: a file-name race (now an atomic `O_CREAT|O_EXCL` reservation), body buffered before authentication (a device guard now runs before any body parser), an unbounded anti-replay cache (now a hard cap with amortized FIFO eviction), and a descriptor leak on an interrupted download (the disk stream is now destroyed as soon as the connection closes). Full French write-up: [securite.md](securite.md).
